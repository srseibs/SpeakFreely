## Code Quality & Pre-Review Standards (Production-Grade First Pass)

- **Pre-Reviewed Code Guarantee**: All code generated or modified by the AI MUST meet full
  production-grade quality standards on the first pass. Prototyping code with "it works for now"
  hacks, missing safeguards, or deferred quality is strictly prohibited.
- **Atomic Database Transactions**: Every multi-statement database modification (e.g., bulk inserts,
  table attachments, multi-row updates) MUST be wrapped in explicit atomic SQLite transaction
  blocks (`db.transaction { ... }` or `db.beginTransaction() / setTransactionSuccessful() / endTransaction()`)
  to guarantee ACID atomicity and prevent table state corruption on power loss or app crashes.
- **Defensive Error Handling & Exception Boundaries**: Wrap non-deterministic operations (e.g., file I/O,
  database attachments, network calls) in explicit `try/catch/finally` blocks with proper cleanup
  and error logging. Never swallow exceptions silently or leave orphan temporary files on failure.
- **Null Safety & Type Contracts**: Enforce strict nullability contracts. Avoid forced unwrapping (`!!`)
  or unverified casts. Ensure fallback branches handle missing data gracefully.
- **Coroutine & Concurrency Safety**: Ensure reactive flows and coroutines never execute heavy, blocking
  I/O or database calls synchronously inside reactive transformation lambdas (such as `combine`).
  Isolate asynchronous operations into dedicated flow streams to prevent UI lag or typing dropouts.

## Dependency Management

- In `libs.versions.toml`, always use the `module = "group:name"` format instead of separate `group`

- **Mandatory Maven Version Lookup**: Before proposing, adding, or modifying any dependency version
  in `libs.versions.toml` or `build.gradle.kts`, the AI MUST execute a `version_lookup` tool query
  to verify the current stable release on Maven. Hardcoding or assuming version strings without a
  `version_lookup` check is strictly prohibited.

## Repository & Data Strategy (One-Shot vs. Streams)

- **One-Shot Operations**: Use `suspend` functions for single-use gets, network API calls, or
  transactional updates. Do not wrap simple one-shot operations in `Flow` as it introduces
  unnecessary wrapper complexity.
- **Reactive Streams**: Use `Flow` strictly for continuous data streams, database observation (e.g.,
  Room `@Query` streams), real-time updates, or active user session observers.
- **`observe*` Naming Prefix for Reactive Streams**: For functions returning continuous `Flow`
  reactive streams (in DAOs, Repositories, and DataSources), use the `observe` prefix (e.g.,
  `observeFavoriteDrinkIds()`, `observeMyBarIngredients()`, `observeUserSession()`). Reserve
  `get*` / `fetch*` for `suspend` one-shot operations. This makes it instantly obvious at the call
  site how the caller should consume the data.
- **Pragmatic Mixing**: ViewModels should embrace mixing `Flow` (for observable state) and `suspend`
  functions (for one-shot loads/actions) rather than forcing all repository return types into
  `Flow`.

## ViewModel Pattern (Initialization & State Management)

- **Embrace `init {}` for One-Shot Fetches**: Do not fear `init {}` for testability reasons.
  Launching `viewModelScope.launch` in `init {}` for one-shot `suspend` repository calls is clean,
  idiomatic Kotlin. With `StandardTestDispatcher` and arranging mocks before ViewModel
  instantiation, `init {}` code is fully deterministic and easy to test.
- **Reactive Streams via `onStart`**: For continuous `Flow` pipelines (e.g., observing database
  queries), use `.onStart { }` paired with `stateIn(SharingStarted.WhileSubscribed(5_000L))` to
  lazily start observation when the UI subscribes.
- **Load Guarding (`AtomicBoolean`)**: Use an `initialLoadGuard` (`AtomicBoolean`) or state check
  inside `.onStart { }` *only* when triggering one-shot side-effects inside a `WhileSubscribed` flow
  pipeline to prevent duplicate network calls across UI re-subscription
```kotlin
class SampleViewModel(
    private val productRepository: ProductRepository, // Contains suspend functions
    private val userRepository: UserRepository        // Contains Flow streams
) : ViewModel() {

    private val _oneShotState = MutableStateFlow(OneShotData())

    // Combine continuous Flow from repo with local StateFlow populated by one-shot suspend calls
    val uiState: StateFlow<UiState> = combine(
        _oneShotState,
        userRepository.observeUserSession() // Flow stream
    ) { data, session ->
        UiState(items = data.items, user = session.user, isLoading = data.isLoading)
    }.stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5_000L),
        initialValue = UiState()
    )

    init {
        // One-shot suspend fetch triggered in init {}
        loadInitialData()
    }

    private fun loadInitialData() {
        viewModelScope.launch {
            _oneShotState.update { it.copy(isLoading = true) }
            val items = productRepository.getProductsSuspend() // suspend call
            _oneShotState.update { it.copy(isLoading = false, items = items) }
        }
    }
}
```

## Domain Naming Precision

- In Domain models and Navigation, favor explicit identifiers (e.g., `personId`, `movieId`,
  `productId`) over a generic `id`. This reduces ambiguity when dealing with nested objects or
  cross-references between different entities.

## Navigation (Compose)

- **Type-Safety**: Always use Compose type-safe navigation (via Kotlin Serialization). Avoid
  string-based route definitions.
- **Hoisting**: Never pass `NavController` directly into Composable Screens. Instead, use callback
  lambda hoisting for all navigation events to keep screens decoupled and testable.
- **Back Navigation**: Prefer `navController.navigateUp()` over `popBackStack()` for back navigation
  events to safely prevent over-popping backstack issues.

## UI Development (Responsive & Performance)

- **Screen/Content Separation**: Split screens into two layers:
    - `XxxScreen`: Top-level Composable that observes the `ViewModel` and handles navigation
      hoisting (passing lambdas to `AppNavigator`).
    - `XxxScreenContent`: Pure, stateless Composable that is ignorant of the `ViewModel` and
      `NavController`. It accepts state and event lambdas as parameters, enabling easy Previews and
      UI testing.
- **Layout Principles**: Prioritize relative sizing and constraints (e.g., `BoxWithConstraints`,
  percentages) over hardcoded DP values for high-level layout containers to ensure adaptability
  across form factors.
- Use separate `item {}` blocks in `LazyColumn` for distinct sections. This optimizes performance
  via lazy composition and allows for consistent spacing using `Arrangement.spacedBy`.
